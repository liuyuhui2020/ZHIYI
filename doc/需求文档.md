## 1. 文档目的

本文定义 ZHIYI Agent Runtime Platform 的目标用户、业务范围、功能需求、非功能需求和阶段验收标准。本文描述“系统必须做到什么”，不规定具体代码实现。

ZHIYI 是项目代号，可在进入实现前调整。本文中的“平台”均指面向开发者、自托管、基于 LangChain 生态的 Agent 运行平台。

## 2. 产品目标

平台要让开发者能够定义、发布、运行和评估具备以下能力的 Agent：

- 调用不同大模型，并根据模型能力进行校验和受控降级。
- 根据场景、任务、记忆、知识和工具结果组装上下文。
- 在有边界的 Agent Loop 中调用本地 Tool 或 MCP Tool。
- 对高风险操作执行确定性策略判断和人工审批。
- 在进程崩溃、网络中断和人工等待后继续执行。
- 通过稳定事件协议输出进度、消息、Tool、审批和结果。
- 记录可脱敏的 Trace、成本、评测和审计信息。

平台不以“能完成一次演示”为成功标准，而以可恢复、可约束、可审计、可评测为成功标准。

## 3. 目标用户与角色

### 3.1 Agent 开发者

使用 Python SDK 定义 Agent、Tool、Context Provider、Memory Policy 和评测集。开发者需要快速调试，同时能够明确控制运行边界。

### 3.2 平台运维人员

部署和升级 Runtime，查看健康状态、Run 队列、故障、资源和成本，处理无法自动确认结果的 Tool 调用。

### 3.3 业务使用者

通过上层应用提交任务、查看流式进度、获得带引用和 Artifact 的结果。业务使用者不直接操作 LangGraph 或模型 Provider。

### 3.4 审批人员

对需要审批的 Tool 调用执行批准、修改或拒绝。审批人员只能处理权限范围内的任务。

### 3.5 租户管理员

配置 Agent 可见范围、Tool 权限、数据留存和用户角色。首期不包含套餐、计费和租户自助开通。

## 4. 参考业务场景

首个参考应用为“企业知识与操作 Agent”：

1. 用户提交一个需要知识检索和业务操作的任务。
2. Agent 检索授权知识，读取业务数据并保留来源链。
3. Agent 根据任务复杂度直接调用 Tool，或先生成结构化 Plan。
4. Agent 提议执行写操作。
5. Policy Engine 判定需要人工审批。
6. 审批人员批准、编辑或拒绝操作。
7. Agent 在审批后继续执行，写 Tool 使用幂等键。
8. 即使 Worker 重启，Run 也能从持久化状态继续。
9. 用户收到带引用、Artifact、警告和用量的结构化结果。

该场景用于验证平台能力，不限定平台只能服务企业知识场景。

## 5. 核心业务对象

| 对象 | 说明 |
|---|---|
| Tenant | 数据与权限隔离边界 |
| AgentDefinition | 可持续演进的 Agent 逻辑定义 |
| AgentVersion | 不可变的可运行版本，固定 Graph、Prompt、Tool 和策略摘要 |
| Session | 用户交互和业务上下文容器 |
| Task | 用户希望完成的独立目标 |
| Run | 一次异步执行尝试，固定 AgentVersion |
| Step | Run 内可观测的执行步骤 |
| ToolInvocation | 一次经过策略处理的 Tool 调用 |
| Approval | 对受控操作作出的审批决定 |
| MemoryRecord | 受策略治理的长期记忆 |
| Artifact | 文件、大结果或生成物的一等引用 |
| RunEvent | 面向客户端的持久化事件 |
| RunResult | Run 的稳定结构化终态结果 |

## 6. 功能需求

### FR-001 Agent 定义与版本

- 平台必须提供 Code-first Python API 定义 Agent。
- 常规 Agent 应通过 `AgentSpec` 声明模型、Tool、Context、Memory、预算和审批策略。
- 复杂 Agent 必须能够提供自定义 LangGraph `StateGraph`。
- 每次发布必须生成不可变 AgentVersion。
- 每个 Run 必须固定一个 AgentVersion，运行中不得漂移。
- 新版本不得原地修改已经被 Run 引用的旧版本。
- 生产 Agent 不得自动修改自己的 Prompt、策略或 AgentDefinition。

### FR-002 Session、Task 与 Run

- 平台必须允许在 Session 中创建一个或多个独立 Task。
- Task 的每次执行必须创建独立 Run。
- Run 是唯一标准执行模型，SDK 同步接口只能封装“创建并等待 Run”。
- 同一 Session 内的并发 Run 必须使用独立图线程，避免状态并发写入。
- Run 必须具有稳定 ID、租户、AgentVersion、状态、预算、创建时间和终态。

### FR-003 Agent Loop

- 默认执行模式必须是受限 Tool-Calling Loop。
- 复杂任务可由策略启用结构化 Planning。
- Plan 必须是可验证、可更新的运行状态，不得把原始思维链作为产品接口。
- Loop 必须限制运行时间、步骤、模型调用、Tool 调用、Token 和成本。
- 超过限制时必须进入明确的 `limit_exceeded` 终态。
- 平台不得保存、展示或依赖模型原始 Chain-of-Thought。

### FR-004 异步执行与恢复

- 创建 Run 后必须快速返回 `run_id`，执行不得依赖请求连接存活。
- Worker 必须通过持久化队列领取 Run，并使用租约防止并发领取。
- Worker 故障后，其他 Worker 必须能够回收过期租约。
- LangGraph Checkpoint 必须用于图执行恢复。
- 产品 Run、Step、Tool、Approval 和 Event 必须独立持久化，不能以 Checkpoint 代替审计记录。
- 所有 Run 必须最终进入成功、失败、取消、超限、等待审批或等待人工处理等明确状态。

### FR-005 模型管理

- 模型层必须通过平台 Model Gateway 接入 LangChain Provider。
- M1 正式支持 OpenAI 和 Anthropic。
- Agent 必须声明 Tool Calling、Structured Output、多模态、上下文窗口等所需能力。
- 运行前必须校验模型能力。
- Fallback 只能在能力兼容的候选模型间发生。
- 模型调用必须支持超时、有限重试、限流、熔断和用量记录。
- V1 不提供由另一个 LLM 决定模型路由的自动路由器。

### FR-006 Context Engine

- 平台必须统一组装上下文，Agent 不得绕过安全层自行替换完整上下文。
- 上下文优先级必须是：平台策略、Agent 策略、场景指令、当前任务、长期 Memory、RAG/业务数据、最近会话、Tool 结果。
- 每个 ContextItem 必须包含来源、优先级、可信等级、敏感等级和 Token 估算。
- 系统必须为输出预留 Token，超预算时按策略裁剪或摘要。
- 低信任检索内容和 Tool 结果不得覆盖高信任策略。
- 每次模型调用必须生成 Context Manifest，以支持调试和评测。

### FR-007 Memory

- 短期 Memory 必须自动维护，并支持裁剪、摘要和恢复。
- 长期 Memory 必须经过 Memory Policy，模型只能提出写入建议。
- 长期记录必须包含租户、主体、Agent、命名空间、来源、置信度、敏感级别、时间和可选 TTL。
- 平台必须支持查看、更正和删除长期 Memory。
- 完整对话不得默认作为永久 Memory 保存。
- Memory 检索和删除必须执行租户与主体权限检查。

### FR-008 RAG 与 Citation

- 文档摄取必须保留文档版本、位置、解析器版本、权限和内容哈希。
- 检索必须先执行租户和访问权限过滤。
- 实际发送给模型的 Chunk 必须记录在 Context Manifest 中。
- 依赖检索事实的回答必须输出 Citation。
- 文档更新必须创建新版本，历史 Run 仍需能够定位原来源。
- 信息不足或只有推断时，结果必须明确说明不确定性。

### FR-009 Tool Registry

- 未在平台 Tool Registry 注册的 Tool 不得暴露给模型。
- 每个 Tool 必须声明名称、版本、Schema、权限、风险、超时、结果上限、副作用类别和并行安全性。
- LangChain `@tool` 是本地 Tool 适配器，不是平台事实源。
- MCP Tool 必须适配到同一 Registry 和 Policy 模型。
- 缺少可信风险元数据的 MCP Tool 必须采用保守默认值并显式启用。
- V1 不允许运行时上传 Python Tool 代码。

### FR-010 Tool 执行可靠性

- Tool 调度语义为 At-least-once，不承诺 Exactly-once。
- 写 Tool 必须使用由租户、Run、Tool Call 和 Tool 版本组成的稳定幂等键。
- 已完成调用必须在恢复时复用持久化结果。
- 外部副作用已发出但结果不可确认时，必须标记 `outcome_unknown` 并停止自动重试。
- 只读且并行安全的 Tool 才能并发执行。
- Tool 参数校验失败、超时、拒绝、输出超限和内部失败必须返回类型化结果。

### FR-011 Policy 与审批

- Tool 是否允许执行必须由确定性 Policy Engine 判断，模型无权绕过。
- Policy 输出必须限制为 `allow`、`deny`、`require_approval`。
- 审批必须支持批准、修改和拒绝。
- 修改后的参数必须重新执行 Schema 和 Policy 校验。
- 审批必须记录操作者、权限、决定、理由、时间和有效期。
- 等待审批的 Run 必须能够跨重启继续。

### FR-012 Artifact

- 上传文件、大 Tool 结果、报告和中间产物必须作为 Artifact 管理。
- 图状态和事件只保存 Artifact 引用，不嵌入大对象。
- Artifact 必须包含租户、MIME、大小、哈希、来源、敏感级别、TTL 和权限。
- M1 支持 TXT、Markdown 和 PDF 文本提取与分块。
- 下载必须使用短时授权访问机制。

### FR-013 Subagent

- M2 支持受控 Subagent，不支持自治 Agent 网络。
- 主 Agent 必须拥有最终任务、预算和结果责任。
- Subagent 必须使用独立上下文和更小预算。
- Subagent 默认只能使用只读 Tool。
- Subagent 只能返回结构化结果或 Artifact，不得直接修改主 Agent 状态。
- 必须限制委派深度、数量和总预算。

### FR-014 REST 与 SSE

- REST 必须用于创建和查询资源、取消 Run、提交审批。
- SSE 必须用于消息、进度、Plan、Tool、审批、Artifact 和终态事件。
- RunEvent 必须持久化并具有 Run 内单调序号。
- 客户端必须能够通过 `Last-Event-ID` 断线续传。
- 慢客户端和断开连接不得阻塞 Agent 执行。
- 对外协议不得暴露 LangGraph 或模型 Provider 的原始事件结构。

### FR-015 RunResult

- 每个终态 Run 必须生成稳定的 `RunResult`。
- 基础字段至少包含：状态、答案、Citation、Artifact、警告、审批摘要、用量、模型版本、AgentVersion 和错误码。
- 业务 Agent 可以扩展结果 Schema，但不得删除基础字段。
- 错误信息必须面向客户端脱敏，并提供内部关联 ID。

### FR-016 可观测与评测

- 平台必须提供结构化日志、指标接口和分布式 Trace。
- Langfuse 是唯一生产 LLM 观测与评测平台。
- Langfuse 不可用时不得影响 Agent 运行结果。
- 每个 Run Attempt 对应一个 Trace，节点、模型、RAG、Memory 和 Tool 对应 Observation。
- 敏感数据必须在应用侧脱敏后再上报。
- AgentVersion 必须通过正确性、Tool 使用、安全、延迟和成本评测门禁后才能发布。

### FR-017 Prompt 管理

- 平台安全策略和核心系统 Prompt 必须由 Git 管理。
- 业务 Prompt 可通过 PromptRegistry 和 Langfuse 进行版本及实验管理。
- Run 启动时必须解析并固定 Prompt 快照。
- Langfuse 不可用时必须使用缓存或已发布回退版本。
- 安全和授权策略不得存储在 Langfuse 中作为唯一来源。

### FR-018 开发者控制台

- M1 提供 Agent 与版本列表、Playground、Run 时间线、审批箱、Memory 管理和 Langfuse 跳转。
- 控制台必须通过平台 REST/SSE 使用能力，不得直接访问运行数据库。
- 控制台不得展示原始 Chain-of-Thought。
- V1 不提供拖拽式 Graph 编辑器。

### FR-019 多租户与认证

- 所有业务数据必须包含 `tenant_id`。
- 仓储接口必须显式接收 Tenant Context。
- 跨租户资源访问必须返回不泄露资源存在性的结果。
- 开发环境可使用静态 API Key。
- M2 必须提供 OIDC/RBAC 接入能力。
- 首期不包含套餐、计费和租户自助运营。

### FR-020 数据留存

- Run 恢复所需内容默认保留 30 天，并支持租户缩短周期。
- 不含敏感正文的结构化审计默认保留 180 天。
- Artifact、Memory 和 Trace 必须分别配置生命周期。
- 安全审计不得被普通用户关闭。
- 删除操作必须记录审计事件，但不得在日志中复制已删除的敏感内容。

## 7. 非功能需求

### NFR-001 可用性

- Runtime API 月度可用性目标为 99.9%。
- 第三方模型不可用必须表现为受控降级或明确失败。
- Langfuse故障不得降低 Agent Runtime 可用性。

### NFR-002 恢复时间

- Worker 故障后，可恢复 Run 应在 30 秒内被其他 Worker 接管。
- 系统必须能够识别并修复永久停留在 `running` 的过期租约。

### NFR-003 性能

- RunEvent 持久化到在线客户端的额外延迟 p95 小于 500 ms。
- 单 Worker Pool 初始基线为 100 个活跃 Run。
- 所有列表接口必须分页，所有高频查询必须具有租户和状态相关索引。

### NFR-004 安全

- 必须执行最小权限、租户隔离、输入校验、输出脱敏和密钥隔离。
- 动态代码执行、任意 Shell、任意 SQL 和不受控文件系统访问默认禁止。
- Prompt Injection 测试、越权测试和敏感数据泄漏测试必须进入发布门禁。

### NFR-005 一致性

- 产品记录是业务事实源，LangGraph Checkpoint 是恢复状态源，两者语义不得混用。
- 状态更新、审计和事件必须具有幂等保护。
- 无法跨外部系统建立原子事务时，必须显式暴露不确定结果。

### NFR-006 可维护性

- 领域层不得依赖 LangChain、LangGraph、Langfuse、FastAPI 或数据库 ORM 类型。
- Provider、Tool、Memory、Trace 必须通过端口和适配器扩展。
- 依赖版本必须锁定，并通过契约测试升级。

### NFR-007 可部署性

- Runtime 必须以 OCI 容器交付。
- 本地使用 Docker Compose，生产提供 Kubernetes/Helm 参考部署。
- 平台核心不得依赖 Kubernetes API，允许部署到 VM、ECS 等环境。
- 数据库迁移必须作为独立且可回滚的发布步骤执行。

## 8. 阶段范围与验收

| 阶段 | 核心范围 | 阶段验收 |
|---|---|---|
| M0 Runtime Alpha | AgentSpec、异步 Run、LangGraph Loop、Fake Model、只读 Tool、Checkpoint、SSE | 可恢复、可续传、受预算约束、确定性测试通过 |
| M1 Platform Beta | 双 Provider、Context、Memory、RAG、Artifact、审批、写 Tool、Langfuse、控制台 | 参考场景完整跑通，安全与恢复语义验证通过 |
| M2 Production V1 | MCP、Subagent、OIDC/RBAC、评测门禁、Helm、压测和安全审计 | 达到 SLO，可滚动升级和回滚，可对外生产使用 |

## 9. 明确不在 V1 范围

- 公有 SaaS 控制面、计费与套餐。
- 运行时上传任意代码。
- 完整 Tool Marketplace。
- 自治多 Agent 网络和无限委派。
- 拖拽式 Graph 编辑器。
- 完整隔离网商业交付认证。
- TypeScript Agent Runtime SDK。
- 自动自我修改 Prompt 和策略。
- 对外部副作用承诺 Exactly-once。

## 10. 需求变更规则

- 任何改变功能行为、数据语义、权限、状态机或阶段范围的变更都必须先更新
  当前 Spec Kit feature 的 `spec.md`，并按影响同步本文。
- 技术实现不得通过代码事实反向覆盖未确认的产品规则。
- 若需求与[技术方案](./技术方案.md)冲突，先记录决策并更新文档，再开始实现。
- 实现前必须完成 `plan.md`、`tasks.md` 和 `$speckit-analyze`；实现后必须
  完成 `drift-report.md` 并通过仓库设计漂移门禁。
- 项目进度、风险和阶段门禁维护在 [PROJECT.md](./PROJECT.md)。
