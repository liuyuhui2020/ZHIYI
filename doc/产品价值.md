> 版本：v0.1
> 更新日期：2026-08-21
> 关联文档：[需求文档](./需求文档.md) · [功能文档](./功能文档.md) · [项目计划](./PROJECT.md)

## 1. 一句话价值

ZHIYI 帮助开发者把“会调用模型和 Tool 的 Agent Demo”变成“可以恢复、约束、审批、审计和持续评测的生产系统”。

## 2. 要解决的问题

开发一个能够调用大模型和 Tool 的 Agent 并不困难。真正困难的是让它在生产环境中长期运行：

- 模型输出存在不确定性，Provider 能力和行为并不完全一致。
- 长任务会遭遇进程重启、网络中断、人工等待和重复执行。
- Tool 一旦具有写入能力，就会出现权限、审批、幂等和未知结果问题。
- 上下文不断增长，简单拼接 Prompt 会造成成本膨胀、指令冲突和数据泄漏。
- 自动保存所有对话并不等于 Memory，反而可能形成错误事实和隐私负担。
- 普通日志无法还原 Agent 为什么选择某个 Tool、使用了哪些知识和消耗了多少成本。
- Agent 版本升级如果缺乏评测门禁，会把 Prompt、模型或 Tool 的回归直接带到生产。

现有框架通常解决其中一个部分。ZHIYI 的价值是把执行、上下文、Tool 安全、Memory、事件和评测组合成一个有明确工程语义的平台。

## 3. 目标用户价值

### 3.1 对 Agent 开发者

- 用 Python 和 LangChain 生态定义 Agent，不必重新封装所有模型 Provider。
- 通过 AgentSpec 覆盖常规场景，复杂场景仍可使用自定义 StateGraph。
- 使用稳定 Runtime API，而不是把 LangGraph内部对象暴露给业务应用。
- 用 Fake Model、契约测试和评测集验证行为，而不是依赖人工试聊。
- 一次定义 Tool 的 Schema、风险、权限和幂等属性，由平台统一执行。

直接收益：更少的重复基础设施代码，更快定位失败，更容易安全迭代。

### 3.2 对业务使用者

- 提交任务后可以持续看到进度，即使断线也能恢复事件。
- 高风险操作在执行前需要明确审批。
- 结果包含来源、Artifact、警告和不确定性，而不是只有一段自由文本。
- 长任务不会因浏览器关闭或服务滚动升级直接丢失。

直接收益：Agent 行为更可预期，结果更容易核验，对自动操作更敢于授权。

### 3.3 对平台运维人员

- Run、模型、Tool、Token、成本和错误具有统一关联 ID。
- Worker 故障后可以回收任务，不需要人工猜测是否执行完成。
- Langfuse用于分析模型质量和成本，产品数据库保留可靠审计。
- API 与 Worker 可独立水平扩容，首期基础设施仍保持简单。

直接收益：故障可诊断、容量可度量、升级可回滚。

### 3.4 对安全与治理人员

- 所有 Tool 都有版本、风险等级、权限和审计策略。
- Policy Engine 而不是模型决定是否需要审批。
- Memory、Trace 和 Artifact 具有独立生命周期和删除能力。
- 租户隔离、Prompt Injection、越权和敏感数据泄漏进入发布门禁。

直接收益：Agent 能力扩展不再等于绕过已有安全边界。

## 4. 核心价值支柱

### 4.1 可恢复的执行

Run 是持久化异步任务。LangGraph负责 Checkpoint 和 Interrupt，平台负责 Run、Step、Event 和租约。进程故障后可以继续执行，人工审批也不依赖原始请求连接。

### 4.2 可治理的上下文

Context Engine 按固定信任和优先级组装上下文，记录实际输入清单，并在 Token 超限前进行裁剪或摘要。检索内容不能覆盖安全策略。

### 4.3 安全的 Tool 行为

Tool 不是任意函数列表，而是经过注册、授权和策略判断的命令。写操作必须考虑幂等和结果不确定性，高风险行为需要审批。

### 4.4 有边界的 Memory

短期 Memory 服务当前会话，长期 Memory 只保存经过策略判断的稳定信息。每条记录有来源、范围、敏感等级、TTL 和删除能力。

### 4.5 可度量的质量

每个 AgentVersion 都能关联模型、Prompt、Tool、数据集、Token、延迟、成本和评分。评测不是报表，而是发布门禁。

### 4.6 可替换的技术边界

LangChain、LangGraph和 Langfuse 各自承担擅长的部分，产品领域模型不依赖其 SDK 类型。平台可以升级或替换适配器，而不重写产品协议。

## 5. 与常见方案的差异

| 常见方案 | 通常解决的问题 | ZHIYI 的补充价值 |
|---|---|---|
| 直接调用模型 SDK | 模型请求与流式响应 | 增加持久 Run、Tool、Context、Memory 和治理 |
| LangChain Agent | 通用 Tool-Calling Loop | 增加产品领域模型、预算、审批、版本和审计 |
| LangGraph | 有状态图执行与恢复 | 增加租户、API、事件、Tool 可靠性和产品事实源 |
| Langfuse | LLM Trace 与评测 | 增加不依赖观测平台的运行正确性和审计 |
| 业务自建 Agent | 针对单场景快速交付 | 抽取可复用 Runtime，同时保留场景扩展能力 |

ZHIYI 不试图替代这些组件，而是定义它们之间缺失的产品与工程契约。

## 6. 产品原则

1. **运行正确性优先于演示效果。** 失败必须可诊断，副作用必须可控制。
2. **产品拥有语义。** 框架对象不能成为对外 API 或业务事实源。
3. **默认安全。** 未注册、未授权、未知风险的 Tool 默认不可执行。
4. **显式优于隐式。** Memory 写入、审批、Fallback、预算和版本都必须可观察。
5. **结果可验证。** 有知识依据的结论必须带 Citation，不确定性必须被表达。
6. **先单 Agent，再受控 Subagent。** 不用多 Agent 掩盖上下文和工具设计问题。
7. **渐进复杂。** PostgreSQL 能满足首期需求时，不提前引入更多分布式基础设施。
8. **不制造虚假保证。** 外部副作用采用 At-least-once 与幂等，不宣称 Exactly-once。

## 7. 价值验证指标

### 7.1 开发效率

- 一个新 Agent 从定义到首次可运行的时间。
- 新增一个 Tool 所需的代码和配置量。
- Provider 切换是否需要修改领域和 API 层。
- 故障从发现到定位根因的时间。

### 7.2 运行质量

- Run 成功率和明确终态覆盖率。
- Worker 故障后的恢复成功率和恢复时间。
- Tool 参数准确率、审批率、拒绝率和未知结果率。
- 断线续传成功率。

### 7.3 Agent 质量

- 参考评测集正确率。
- Citation 有效率。
- Tool 选择与参数准确率。
- 不应调用 Tool 的负样本通过率。
- Prompt Injection 和越权测试通过率。

### 7.4 成本与性能

- 单任务 Token 和模型成本。
- 单任务模型调用与 Tool 调用次数。
- RunEvent 交付延迟。
- 单 Worker Pool 活跃 Run 数量和数据库负载。

## 8. 价值假设与验证方法

| 假设 | 验证方式 | 失败信号 |
|---|---|---|
| 开发者需要统一 Runtime，而非继续自建 | M0 用第二个 Agent 接入验证复用成本 | 第二个 Agent 仍需改 Runtime 核心 |
| LangGraph 能降低恢复实现成本 | 强制终止 Worker 并验证 Run 恢复 | 大量恢复逻辑仍需绕开 LangGraph |
| Tool Registry 能减少风险 | 用一个审批写 Tool 做故障与重试测试 | Tool 仍可绕过策略或重复副作用 |
| Context Engine 能提升稳定性 | 比较固定上下文集的质量和 Token | 上下文清单不可解释或成本无改善 |
| Langfuse足以支撑评测闭环 | 对两个 AgentVersion 做数据集对比 | 无法稳定关联版本、成本和得分 |
| PostgreSQL 足以支撑首期队列 | 100 个活跃 Run 压测 | 领取、事件或 Checkpoint 形成明显瓶颈 |

## 9. 不提供的价值

ZHIYI V1 不承诺：

- 让任意业务无需工程投入自动变成 Agent。
- 通过更多 Agent 数量自然获得更高质量。
- 消除模型幻觉或第三方模型故障。
- 对所有外部副作用实现 Exactly-once。
- 提供一个可运行不受信任代码的通用沙箱。
- 同时成为完整 SaaS、工作流平台、模型网关和 Tool Marketplace。

- **M1 Platform Beta：** 证明“企业知识与操作场景可以安全、可解释地闭环”。
- **M2 Production V1：** 证明“平台能够按 SLO 部署、升级、扩容和治理”。
