## User Scenarios & Testing *(mandatory)*

### User Story 1 - 跨进程持久保存 Run 事实 (Priority: P1)

作为 Runtime 开发者，我希望已经创建或推进的 Run、事件和命令收据在进程退出后仍能
完整读取，从而让后续 API、Worker 和恢复协调器建立在同一份持久业务事实之上。

**Why this priority**: 当前内存仓储只验证契约，进程退出即丢失全部状态；没有持久事实源，
后续任何异步执行或恢复能力都无法成立。

**Independent Test**: 在一个全新数据环境中提交覆盖创建、非终态转换、预算消耗和四类
终态的 Run，关闭原访问实例后由新的独立实例读取，验证 Run、事件和命令收据与提交前
的领域值完全一致。

**Acceptance Scenarios**:

1. **Given** 一个通过既有生命周期契约创建的 Run，**When** 首个访问实例结束后由新实例读取，**Then** Run 的身份、固定 AgentVersion、状态、版本、预算、累计用量、时间和结果保持一致。
2. **Given** 一个 Run 已产生多条合法事件，**When** 新实例从任意合法序号分页读取，**Then** 只返回该序号之后的事件，并保持连续顺序和稳定内容。
3. **Given** 一个命令已经成功提交，**When** 在进程重启后以相同命令标识和相同意图重试，**Then** 返回原命令收据和原事件，不产生新的状态、用量或事件。
4. **Given** 一个终态 Run，**When** 重新打开持久化访问并读取结果，**Then** 唯一 RunResult 与终态、AgentVersion 和累计用量一致且不可被后续提交改写。

### User Story 2 - 多实例并发下保持原子与幂等 (Priority: P1)

作为平台维护者，我希望多个应用实例同时提交命令时仍只有合法的单一结果，并且 Run、
事件和命令收据始终全有或全无，从而避免重复投递和竞争写入破坏状态。

**Why this priority**: PostgreSQL 适配器的价值不只是保存数据，还必须把 004 已验证的
进程内原子契约提升为跨连接、跨实例的可靠约束。

**Independent Test**: 使用多个独立访问实例并发执行相同命令、不同命令、过期版本、
冲突意图和故障中断，验证幂等判定优先级、单一获胜者及零部分写入。

**Acceptance Scenarios**:

1. **Given** 多个实例同时提交相同命令标识和相同意图，**When** 请求竞争完成，**Then** 只有一次实际提交，所有成功响应引用同一收据和同一事件。
2. **Given** 多个实例基于同一预期版本提交会改变 Run 或追加事件的不同命令，**When** 请求竞争完成，**Then** 至多一个命令成功，其余请求得到稳定版本冲突，且失败请求不留下收据或事件；不改变 Run 的合法零事件命令可以各自只新增收据。
3. **Given** 一个命令标识已绑定某一意图，**When** 任一实例以不同意图复用该标识，**Then** 返回稳定幂等冲突，不读取或改变该 Run 的业务状态。
4. **Given** 提交遇到存储故障，**When** 系统能证明事务未提交或无法确认提交结果，**Then** 分别返回 `storage_unavailable` 或 `commit_outcome_unknown`；调用方使用原命令安全重试后，最终状态只能是完整提交一次或完整未提交后再提交一次，不出现 Run、事件或收据的部分组合。

### User Story 3 - 租户安全地查询和回放事件 (Priority: P1)

作为平台安全与集成开发者，我希望所有 Run、事件和命令收据都严格位于租户边界内，
并能按稳定游标分页读取，从而让后续 API 和 SSE 不会泄露其他租户的数据或产生错序回放。

**Why this priority**: 持久化层是多租户隔离的最后防线；仅依赖调用方过滤无法抵御遗漏、
并发或直接适配器调用造成的越权。

**Independent Test**: 创建具有相同 Run/命令标识但属于不同租户的数据，执行正向查询、
跨租户负向查询和多页事件回放，验证身份空间相互独立且未授权结果不泄露资源存在性。

**Acceptance Scenarios**:

1. **Given** 两个租户使用相同 Run 标识，**When** 分别读取和更新，**Then** 每个租户只能看到并修改自己的 Run。
2. **Given** 一个 Run 只存在于其他租户，**When** 当前租户读取 Run 或事件，**Then** 返回与资源不存在相同的结果，不暴露所有者或数据内容。
3. **Given** 两个租户使用相同命令标识，**When** 分别提交各自命令，**Then** 两个命令独立处理，不共享收据或幂等冲突。
4. **Given** 一个已有事件的 Run，**When** 按允许的页大小连续读取全部页面，**Then** 每个事件恰好出现一次、顺序严格递增且不会越过租户边界。
5. **Given** 任一租户已经保存某个事件标识，**When** 另一租户尝试提交相同事件标识，**Then** 整次提交以安全不变量错误失败，不泄露原事件归属或内容。

---

### User Story 4 - 安全演进和回退持久化结构 (Priority: P2)

作为部署和运维人员，我希望持久化结构可以通过独立发布步骤在空环境中建立、验证并
按说明回退或恢复，从而降低未来滚动升级和故障处理的数据风险。

**Why this priority**: 首个产品数据库结构会成为后续租约、Worker 和 API 的基础；如果
缺少可重复建立、兼容演进和恢复边界，后续切片会被不可逆的数据耦合锁定。

**Independent Test**: 对一次性可丢弃环境执行从空环境建立、写入代表性数据、验证结构、
执行回退或恢复、再重新建立的完整演练，确认步骤可重复且应用启动不会隐式改变结构。

**Acceptance Scenarios**:

1. **Given** 一个空的受支持数据环境，**When** 执行独立结构升级步骤，**Then** 所需持久化结构被完整建立并能通过仓储验收。
2. **Given** 当前结构已包含代表性 Run、事件和命令收据，**When** 执行已声明的回退或恢复演练，**Then** 结果、数据影响和重新升级步骤与说明一致。
3. **Given** 多个应用实例同时启动，**When** 没有显式执行结构升级步骤，**Then** 任一应用实例都不会自行并发修改持久化结构。
4. **Given** 存储不可用、持久记录损坏或结构版本不受当前应用支持，**When** 仓储操作失败，**Then** 调用方分别得到稳定且脱敏的存储、`data_corruption` 或 `schema_incompatible` 失败，日志和异常不包含连接凭据、原始查询或敏感载荷。

### Edge Cases

- 新建 Run 使用预期版本 0；已存在同租户、同 Run 标识时必须按命令重放或冲突处理，不能覆盖原记录。
- 相同 Run 标识和命令标识可以在不同租户独立存在；`event_id` 例外，必须在所有租户之间全局唯一。任何事件读取和更新仍必须显式校验租户与 Run 边界。
- 相同命令标识、相同意图的重放必须先于预期版本判断；不同意图复用必须先于读取或修改 Run 被拒绝。
- 一个成功命令最多追加一条事件；合法零事件收据只能对应未变化的当前 Run 快照。
- 零事件命令与状态变更命令竞争时，以取得该 Run 当前事实的数据库线性化点为准：状态变更先完成则过期的零事件命令返回版本冲突；零事件命令先确认未变化快照则可只提交收据，后续状态变更仍可基于同一版本继续提交。
- 重复事件标识、事件序号缺口、倒序事件、错误 Run/租户归属或收据与结果不一致时，整次提交必须失败。
- 金额必须保持精确十进制语义；所有符合 004 当前规则的有限非负 `Decimal`，包括超出数据库原生数值精度范围的值，都必须无损往返，不得新增精度/小数位限制、舍入或截断。UTC 时间不得丢失时区或精度，事件载荷与结果引用不得在往返持久化后改变类型或内容。
- 004 接受的 Python 整数和不可变 JSON 整数不得因运行时默认的整数文本转换上限而被缩窄；超出该默认上限的合法值仍须无损往返，且实现不得通过进程级关闭该安全上限来规避编解码责任。
- 持久化可以沿用 004 的规范化十进制表示，因此等值 Decimal 的指数或尾随零文本形式不要求逐字符保留；必须保留数值相等性。若合法值仅因数据库容量、磁盘或单次存储资源不足而无法保存，必须作为已确认未提交的 `storage_unavailable` 处理，不得伪装成领域输入无效、精度超限或成功。
- 请求在提交确认前断开时，能证明事务未提交则返回 `storage_unavailable`；无法证明提交或回滚则返回 `commit_outcome_unknown`，且只能使用原 command_id 与原意图重放确认，不得创建新命令猜测结果。
- 读取不存在的 Run 与读取其他租户的 Run 必须保持不可区分；不存在的事件流不得被误判为空的已授权 Run。
- 非法页大小、负游标和超出当前末尾的游标必须保持既有仓储契约，不得触发无界读取。
- 空环境升级失败、升级中断、回退失败或应用版本与数据版本不兼容时必须停止使用该结构，不得静默猜测或自动修复生产数据。
- 未知状态、非法字段组合或无法解码的持久记录必须返回 `data_corruption`；数据库结构版本超出当前应用声明的兼容范围必须返回 `schema_incompatible`。两者都必须保留安全诊断关联信息，不能被静默转换为合法领域值或互相替代。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 平台 MUST 提供 PostgreSQL 支持的持久 RunRepository，并保持 004 已批准的 RunRepository 调用契约、领域状态、错误优先级和返回语义不变。
- **FR-002**: 持久仓储 MUST 保存并恢复完整的 Run 快照、RunEvent 和 CommandReceipt，包括固定 AgentVersion、版本、连续事件序号、硬预算、累计用量、时间、终态结果、安全错误及稳定引用。
- **FR-003**: 每次提交 MUST 将 Run 快照、零或一条新事件及命令收据作为一个不可分割单元处理；任一校验、冲突或存储失败 MUST 留下零部分更新。
- **FR-004**: 仓储公开参数的类型与基础范围校验 MUST 在存储访问前完成；对已经通过该校验的提交，判定 MUST 依次处理既有命令重放、命令意图冲突、预期版本冲突和聚合不变量校验。数据库约束失败不得改变该优先级，并发窗口也不得把重放误判为版本冲突。
- **FR-005**: 相同租户、相同命令标识和相同规范化意图的请求 MUST 在跨连接、跨实例和重启后返回第一次的确定性收据与事件，不重复改变 Run、预算、结果或事件。
- **FR-006**: 相同租户、相同命令标识但不同意图的请求 MUST 返回稳定幂等冲突；失败请求 MUST NOT 获得原命令的敏感业务内容。
- **FR-007**: 会改变 Run 或追加事件的新命令 MUST 基于当前 Run 版本执行乐观并发控制；同一版本上的这类竞争写入 MUST 至多一个成功，其余请求返回稳定版本冲突。符合 FR-009 的不同零事件命令 MAY 在同一未变化版本上分别只新增收据。
- **FR-008**: 创建提交 MUST 只允许预期版本 0、版本 1 和首条连续事件；已存在的同租户 Run MUST NOT 被覆盖或重新初始化。
- **FR-009**: 零事件提交 MUST 只允许保存指向当前未变化 Run 的新命令收据；其结果状态、版本和事件引用 MUST 与当前事实一致。
- **FR-010**: 每个成功命令 MUST 最多追加一条事件；`event_id` MUST 在所有租户之间全局唯一，事件还 MUST 保持正确租户与 Run 归属、连续递增序号、载荷版本和不可变安全载荷。
- **FR-011**: 持久层 MUST 拒绝任何租户已使用的重复事件标识、重复或不连续序号、错误归属、收据不一致、终态重写及其他违反 004 聚合不变量的提交；重复事件错误不得披露既有事件的租户、Run 或内容。
- **FR-012**: Run 与 CommandReceipt 的身份空间以租户为边界，相同 `run_id` 或 `command_id` MAY 在不同租户独立存在；事件读取、更新、幂等和常用查询也 MUST 显式使用租户边界，即使 `event_id` 全局唯一。跨租户访问与资源不存在 MUST 返回相同公开值、错误码和安全消息，且不得在诊断字段中携带真实所有者或既有内容；本 Feature 不承诺微秒级常量时间，但延迟不得成为返回资源归属信息的接口。
- **FR-013**: 事件读取 MUST 保持既有游标语义：只返回指定序号之后的事件，默认最多 100 条，单次限制为 1 至 1,000 条，并按 Run 内序号严格升序返回。
- **FR-014**: 持久化往返 MUST 无损保留有效标识、枚举、精确十进制金额、UTC 时间、不可变 JSON 值、载荷版本、可选字段和引用集合。005 MUST 接受并按 004 的规范化数值语义无损恢复所有符合当前规则的有限非负 `Decimal`，不得新增精度或小数位上限，也不得舍入或截断；等值 Decimal 的指数或尾随零文本形式 MAY 规范化。内部持久编码可以使用字符串承载数值，但恢复后的领域对象和事件 JSON 值类型 MUST 与提交前一致。不得使用可执行或不透明的对象序列化作为产品事实。
- **FR-015**: 存储层的唯一性与一致性保护 MUST 在多个应用实例之间成立，不能只依赖单进程锁、进程内缓存或调用方先查后写。
- **FR-016**: 连接中断、事务中止、锁/语句超时、死锁、存储连接获取超时或存储资源不足后，仓储能够证明事务未提交时 MUST 返回稳定的 `storage_unavailable`；无法证明事务已提交或已回滚时 MUST 返回稳定的 `commit_outcome_unknown`。两者均不得伪装为成功或领域冲突。仓储内部 MUST NOT 自动重试写事务；调用方如按有限退避策略重试写入，MUST 保留原 command_id 与原规范化意图。`commit_outcome_unknown` 只能在新连接上以该原命令重放确认：若原事务已提交则返回其持久收据，若原事务已回滚且没有收据则同一重放 MAY 完成一次新提交，最终只能收敛到一个完整结果。
- **FR-017**: `storage_unavailable`、`commit_outcome_unknown`、`data_corruption` 和 `schema_incompatible` MUST 是四种不同的稳定脱敏错误。存储不可达时优先返回 `storage_unavailable`，不得推断结构或记录状态；存储可达但应用结构契约不受支持时在读取业务记录前返回 `schema_incompatible`；结构兼容后，无法还原为合法领域事实、投影与权威记录不一致或引用损坏时返回 `data_corruption`。提交确认已经进入未知窗口时，`commit_outcome_unknown` 优先于事后猜测冲突或损坏。公开异常及其可打印表示只允许稳定码、安全常量消息和可选 correlation_id，不得包含 tenant_id、run_id、凭据、连接信息、原始查询、完整事件载荷、最终答案或隐藏推理；内部安全日志可以记录调用方已提供的 tenant_id/run_id，但不得记录冲突资源的真实所有者或内容。
- **FR-018**: 平台 MUST 提供独立、可重复的持久化结构升级步骤；应用进程启动 MUST NOT 自动或并发执行结构升级。
- **FR-019**: 持久化结构变更 MUST 支持从空环境建立、版本识别、滚动升级兼容评估，以及明确的回退或备份恢复步骤；失败时不得伪造已升级状态。
- **FR-020**: PostgreSQL 适配器 MUST 通过与内存适配器相同的共享 RunRepository 契约，并增加真实多连接并发、进程重开、事务故障、结构升级和跨租户负向验收。
- **FR-021**: 验收 MUST 使用真实的、一次性可重建的 PostgreSQL 环境，不得用内存替身或行为桩代替持久化、约束、事务和并发证明。
- **FR-022**: 本 Feature MUST 保持 domain 和 application 层不依赖数据库、迁移工具或持久化实现类型；持久化实现不得反向定义 Run 状态机、事件或结果语义。
- **FR-023**: 本 Feature MUST NOT 修改 004 的 Run 状态矩阵、预算、命令指纹、收据、事件或结果语义；如发现现有契约无法安全持久化，MUST 先通过规格与分析流程同步设计，不能在适配器中静默改变行为。
- **FR-024**: 本 Feature MUST 只交付 Run/Event/CommandReceipt 的 PostgreSQL 持久化、结构版本与迁移、适配器装配边界及相关验证，不包含领取租约、Worker、Reconciler、LangGraph Checkpoint、REST/SSE、SDK、Model Gateway 集成、Tool 执行、Approval、Context、Memory、RAG 或 Langfuse。
- **FR-025**: 本 Feature MUST NOT 创建后台调度循环、占用 Run、续租、回收过期任务或执行 Agent；持久化 Run 不代表 Run 已具备异步执行或故障恢复能力。

### Key Entities

- **Persistent Run Snapshot**: 004 Run 聚合在某一版本的持久业务事实，包含租户作用域、固定 AgentVersion、生命周期状态、硬预算、累计用量、时间、下一事件序号和可选终态结果。
- **Persistent Run Event**: 归属于租户与 Run 的不可变有序事实，保留跨所有租户全局唯一的稳定事件标识、Run 内序号、类型、发生时间、载荷版本和安全载荷。
- **Persistent Command Receipt**: 归属于租户与命令标识的不可变处理结果，绑定 Run、命令类型、规范化意图指纹、结果状态/版本及零或一个事件引用，用于跨进程重放与冲突检测。
- **Atomic Persistence Commit**: 将一个更新后的 Run 快照、零或一个新事件和一个命令收据作为全有或全无结果处理的逻辑事务边界。
- **Persistence Structure Version**: 标识产品持久化结构当前兼容状态的版本事实，用于独立升级、兼容性检查、回退或恢复，不由普通应用实例自动推进。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 内存与持久仓储对共享 RunRepository 验收的通过率均为 100%，且相同输入产生相同领域结果、事件、收据和错误分类。
- **SC-002**: 覆盖全部八种 Run 状态、四种终态、每类事件、零事件收据和各预算维度的代表性数据，在关闭并重新建立访问实例后无损读取通过率为 100%。
- **SC-003**: 对至少 100 个彼此独立的 Run 分组，每组从同一 expected_version 并发提交至少 10 个不同 command_id 且都会改变 Run 或追加事件，累计至少 1,000 次提交；每组至多一个成功，丢失更新、重复事件和部分记录数量均为 0。零事件命令使用独立样例组，验证多个合法不同命令只新增各自收据、不改变 Run 版本，且不计入状态变更单赢家统计。
- **SC-004**: 对同一命令执行 100 次并发请求，至少使用 20 个同时存活且每个至少承担一次请求的独立数据库连接；只产生一次实际状态变化，其余成功结果均为重放，所有结果版本和事件标识相同。另以独立请求复用相同 command_id 与不同意图，拒绝率为 100%。
- **SC-005**: 对提交前、确定回滚和提交确认不明三个故障窗口执行至少 100 次可重复故障验收，前两类被分类为 `storage_unavailable`、第三类被分类为 `commit_outcome_unknown` 的准确率均为 100%；Run、事件、收据不一致组合数量为 0，原命令重试均收敛到确定结果。
- **SC-006**: 覆盖读取、事件分页、命令查找、创建、更新和冲突路径的跨租户负向验收通过率为 100%，向非所属租户泄露的资源存在性或业务字段数量为 0。
- **SC-007**: 对所有已提交事件执行单页和多页回放时，事件重复数、缺口数、倒序数和跨 Run/跨租户混入数均为 0；跨租户重复 `event_id` 的提交拒绝率为 100%，错误内容泄漏数为 0。
- **SC-008**: 至少覆盖 12 个合法 Decimal 样例，包括零、等值不同指数/尾随零输入、20,000 位小数、200,000 位整数以及对应的预算/用量/事件嵌套位置；同时覆盖至少一个 5,000 位非负计数，以及正数、负数各至少一个 5,000 位嵌套 JSON 整数、UTC 边界时间、不可变载荷、可选结果和引用集合。验收进程在测试前后 MUST 保持 Python 默认整数文本转换安全上限不变。以领域数值相等性和恢复后 JSON 类型相等性判断往返，成功率为 100%，舍入、截断或新增语义范围拒绝数量为 0；损坏记录被分类为 `data_corruption`、不兼容结构被分类为 `schema_incompatible` 的准确率均为 100%，被静默接受或错误互换的数量为 0。
- **SC-009**: 从空环境执行建立、验证、回退或恢复、再次建立的演练全部通过；普通应用启动引发的结构变更次数为 0。
- **SC-010**: 使用已知假凭据、连接字符串、原始查询、完整事件载荷、最终答案和隐藏推理标记触发全部成功与失败路径时，公开错误、日志和可打印表示中的敏感标记泄漏数为 0。
- **SC-011**: 在计划声明并固定的本地验收环境、至少 100 个 Run/每个 100 条事件的数据集和 20 个并发客户端下，每类操作先预热至少 100 次，再各测量至少 1,000 次；Run 读取、100 条事件分页和不同 Run 上的无冲突原子提交分别按 nearest-rank 计算 p95，均须小于 100 毫秒。报告 MUST 记录处理器、内存、操作系统、存储环境摘要和并发资源配置，且不得通过放宽一致性、租户隔离或持久一致性保护换取性能。
- **SC-012**: 完成本 Feature 后，租约领取、Worker 执行、Checkpoint 恢复、REST/SSE 和 Model Gateway 调用的新增生产行为数量均为 0；这些能力仍需独立 Spec Kit Feature。

## Assumptions

- 004 Run Lifecycle Kernel 的领域对象、RunRepository 端口、命令判定顺序和共享契约是本 Feature 的上游基线；本 Feature 默认复用而不重新设计。
- PostgreSQL 已由项目架构确定为产品事实源；具体驱动、映射和迁移工具的选择属于后续规划阶段，不在本规格中预设。
- 005 不收紧 004 对成本 `Decimal` 的有效范围；规划阶段必须选择可版本化、可检查且无损的持久表示。
- 当前没有需要从生产内存仓储导入的历史数据；内存适配器继续仅用于快速离线契约测试，不承担数据迁移来源。
- 本 Feature 可以新增首个产品数据库结构，但数据库实例、凭据、备份服务和生产部署由环境提供，不纳入仓储本身。
- 集成验收使用一次性、非生产 PostgreSQL 环境，并允许在测试结束后销毁；任何生产数据操作仍需单独授权。
- 结构升级是发布流水线或运维人员显式执行的独立步骤，应用 API 与未来 Worker 进程只检查兼容性，不自行迁移。
- 初始结构的反向迁移可能删除本 Feature 创建的数据，因此必须明确数据影响，并以备份恢复作为需要保留数据时的回退路径。
- 数据留存、归档、删除、备份周期和跨区域复制将在对应治理或生产化 Feature 中定义；本 Feature 只确保结构可演进并记录恢复要求。
- 租约、Worker 和 Checkpoint 依赖本 Feature 的持久事实源，但不会作为本 Feature 的隐藏验收条件或附带实现。
